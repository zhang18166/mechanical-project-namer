# Phase4C：维护中的HTTP入口与HTTPS隔离验收

2026-10-30。**新入口开发验收PARTIAL**，仅本机Windows→专用Ubuntu22.04隔离链路；不是腾讯云、公网或生产放行。基准`1f980ae078db429b52a18f7650a56996987bfe25`，独立分支`codex/mechanical-workbench-phase4c-https`及工作树`<开发根>/_worktrees/mechanical-workbench-phase4c-https`。原4B工作树和私有历史保留。应用1.7.1、桌面Schema13、服务账号schema3均未变，**Phase2D仍PARTIAL、STEP普通模式关闭**。

## 实现与选型

Windows标准库TLS客户端→普通用户Nginx 1.30.6→私有Unix socket→Uvicorn 0.54.0 / h11 0.16.0→原AccountStore/发布服务。没有HTTP转发到旧HTTPServer，也没有第二套账号、索引、编号或发布状态机。`PublishService/AccountService`抽出共享业务，旧Handler与新Exchange分别实现传输。备份/恢复与最后管理员保护继续用原事务和租约。来源、签名/哈希、依赖许可及补丁版libssl3 3.0.2-0ubuntu1.30见[第三方记录](../../third_party/https/README.md)。

Windows CPython3.12.14/OpenSSL3.5.7、Qt沿用原锁定环境；Linux为原专用WSL2 Ubuntu22.04.5、UID1000、独立CPython3.12.16/SQLite3.53.1/Python ssl OpenSSL3.5.9。只新增用户prefix及独立venv，没有改系统Python、Nginx/default distro/网络或全局证书。运行入口、配置、限额及取消语义详见[HTTPS隔离说明](HTTPS_ISOLATION.md)。

单个应用worker并非天然串行，因此明确只准入一个后台业务操作、排队0、忙时503；哈希/复制/Argon2移出事件循环，重复取消不能提前释放仍在写文件的线程。所有请求使用原实时权限检查，最终commit不沿用过期授权。Nginx只代理API，无静态模型目录，流式请求和响应都不落代理缓存，无共享私有缓存或非幂等自动重试。私有socket及同UID目录是信任边界，不宣传OS安全沙箱。

## 测试与失败记录

原干净基线966通过、0失败/跳过，740.65秒。最终Windows **1088通过、0失败/错误/跳过，1486.319秒**；JUnit逐个核对原966项测试身份全部保留，新增122项，不按脚本内部断言数凑用例。新增为21项独立子进程ASGI回归、54项真实HTTPS角色/操作矩阵、25项真实Nginx/TLS/限额与安全边界、9项真实传输/进程或受控存储故障及13项连接/台账/时限/ready/GUI状态回归。GUI、整体恢复和资源报告另列，不充当额外pytest数量。

Linux最终原生108项unittest通过、0失败/跳过，109.684秒：原87项及21项新ASGI测试。其中99项与Windows重叠，9项为Linux独立路径/权限/锁等检查，不相加凑总数；Windows驱动真实Linux HTTPS服务的场景另外归入Windows测试身份，不能再叠加一次。早期105项通过记录保留，不当作额外108项之外的独立数量。

实际失败保留：

1. 初始Nginx启动仍引用包内默认fastcgi/uwsgi/scgi临时目录，已全部指定为私有prefix，不修改系统目录。
2. 新ASGI直接放入pytest时，原禁网络fixture同时拦截Windows asyncio内部socket pair。改用独立隔离测试子进程，保留主测试禁网规则，未跳过用例。
3. 新门禁测试起初误用元数据键；纠正为实际`recovery_gate`，权限预期仍为拒绝。
4. 新慢传输测试最初误套403辅助断言，实际已产生正确的超时/哈希失败。改为分别核对明确错误码，同时保留实际接收字节、未完整版本及未出现成功下载目标的断言。
5. 旧78项授权矩阵在创建客户端后直接改项目字典，与新增不可变目标绑定冲突，未进入权限断言。夹具改为显式为另一个项目构造客户端，所有原授权/拒绝/数据不变断言保留；整个发布加固文件已复验通过。
6. 新应用上传中硬退出后，曾出现一次Windows重新握手超时，Linux实例已ready；单项复验通过。故障恢复脚本只在该明确超时后核对同一新实例的原生HTTPS健康，再允许一次全验证的公开GET健康重试；不重放凭据/写操作、不放松证书、不无限提高时限。底层瞬态原因未确认，不能宣称已修复WSL/网络栈。
7. 补强“注入必须实际触发”的断言后发现，提交故障配置误带上传阈值，提前消耗同一nonce，原DB/封存/提交确认丢失场景的成功不计有效故障证据。现将两类触发器分开，要求故障事件实际存在；DB/封存还独立读取失败后SQL及正式目录边界，再重跑恢复、文件请求次数和下载哈希。失败记录保留，不因用例返回成功就冒充故障已覆盖。
8. 直接ASGI请求的非ASCII raw_path可令Exchange构造失败，先设的忙碌标志未释放：新增测试实际失败后修复为先验证路由/构造Exchange再占槽，调度失败恢复准入、取消仍由实际线程完成释放；唯一工作线程在接收请求前启动，线程启动失败直接中止启动。增加构造/调度异常后健康请求可继续的回归。实际Nginx链路对同样非法裸URI返回400、后续health200，**未复现代理链路DoS**，不夸大内部发现。
9. 高并行完整回归触发旧发布夹具ready文件存在但JSON尚未写完的原有竞态；在同一个12秒预算内等待完整字段，新增发布成功/有界超时回归，未删原权限断言。修复涉及验收夹具指纹，资源短轮记诊断后重跑，不把它计成最终30分钟。
10. 最后界面验收补齐目标与历史/当前确认提示；新增控件回归先实际失败、实现后通过，再实际启动Windows窗口验证离线历史及重连。此前完整回归和资源轮保留为历史，最终代码从此重新固定计时。
