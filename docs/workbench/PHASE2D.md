2026-10-29，**PARTIAL**。基于公开Phase 2C提交`f4759df3feaa22e7269d9d17dd67b3f228a7b13d`，独立工作树和分支`codex/mechanical-workbench-phase2d-stability`。应用1.7.1、Schema12、项目身份与编号规则保持不变，无数据库迁移。Phase 0至2C历史验收保留。本文件的开发结论与Git同步结论分别记录。

## 实际修复与归因边界

原HTTP服务每个实例创建捕获owner的局部Handler类，形成`ResourceServer → HTTP server → Handler closure → ResourceServer`引用环。关闭后socket虽已关闭，对象及类/锁仍等待循环GC。原30次GLB短测最后有8个服务弱引用存活；禁用循环GC的回归可复现。改为模块级Handler和有界Server、weakref owner、独立异步停止函数，关闭幂等并提供完成事件；仍只绑定回环地址，Host/精确能力路由、8个请求预算及5秒连接超时保留。修复后30次GLB、STL、STEP及40次混合关闭后服务弱引用均为零，不靠强制GC清理。

请求拦截器的allowed/blocked诊断列表原来无限追加，现各保留最多256项；请求判定规则不变。这是容量保护，不把它说成已证明的主要内存增长原因。

同机短测对照如下；每种单格式30次、混合40次，不将初始保留当成持续泄漏，也不由数MiB差异宣称优化成功：

| 格式 | 原代码首轮→末轮关闭后私有MiB | 修复后首轮→末轮关闭后私有MiB | 原/新末轮服务存活 | 原/新末轮句柄 |
| --- | ---: | ---: | ---: | ---: |
| GLB | 333.9→366.5 | 333.9→368.2 | 8 / 0 | 2416 / 2376 |
| PDF | 107.1→109.9 | 109.2→110.9 | 0 / 0 | 1558 / 1550 |
| STL | 327.1→361.4 | 330.6→357.2 | 3 / 0 | 2420 / 2404 |
| STEP | 330.1→364.9 | 332.4→366.5 | 6 / 0 | 2431 / 2400 |
| 混合 | 329.5→432.1 | 336.8→436.1 | 6 / 0 | 2447 / 2426 |

这批数据证明服务对象释放改善，没有证明主进程私有内存整体降低。空闲对照原代码120.9秒/116次采样、修复后301.0秒/288次采样，末端私有字节约90.7/89.8 MiB；时长不同，仅用于排除完全不打开预览时的同量级增长。

没有窗口/view/page/profile/拦截器弱引用逐轮累积；Qt存活QObject在关闭后为390个，包含文件管理页面的固定控件。PDF短测接近平台，而三种WebEngine格式都有初期较大保留。强制GC的旧代码追踪对照中，第10至30轮Python追踪堆约7.50→7.54 MB，私有字节仍有增长；主要差额不在Python追踪堆，尚不能准确指向某个Qt/Chromium原生分配栈，也不能证明全部是正常缓存。

曾A/B尝试共享一个隔离WebEngine profile，30轮GLB私有字节333→369 MiB，与原方案没有改善；已撤回，不纳入最终代码。原内存测量函数与静态ctypes版本分别执行10,000次，控制进程私有字节和句柄稳定，不把测量函数误判为根因。

## 环境与重复执行

独立venv沿用锁定的PyQt6/WebEngine绑定6.11.0、Qt/WebEngine运行库6.11.2、Chromium140.0.7339.225，Online 3D Viewer0.18.0、occt-import-js0.0.23。未全局升级，`pip check`通过。资源安装使用原`setup_cad.ps1 -WithFixtures`；OCP仍只在子进程生成我们自己的模型，不读取用户CAD。运行时预览没有互联网依赖，也未禁用沙箱、Web安全或证书校验。

在本Phase 2D工作树执行：

```powershell
.\scripts\dev_stability.ps1
.\scripts\dev_stability.ps1 -Smoke
.\scripts\test_workbench.ps1
.\.venv\Scripts\python.exe scripts\verify_cad.py --output '<新的仓库外GUI证据目录>'
.\.venv\Scripts\python.exe scripts\profile_previews.py --output '<新的仓库外采样目录>' --mode mixed --cycles 0 --minutes 60 --hold-ms 10000
.\.venv\Scripts\python.exe scripts\analyze_preview_profile.py '<已完成的采样目录>'
```

开发启动默认使用`%LOCALAPPDATA%/MechanicalWorkbenchDev/phase2d`，独立设置、数据库、缓存及单实例身份。命令须在本工作树运行；不会把代码回写旧工作树。分格式诊断将mode改为idle/glb/pdf/stl/step；可用cycles控制次数。trace/collect仅用于归因对照，正式长测不启用，不在产品循环中强制GC或修剪工作集。

采样逐轮记录主/子进程工作集、私有字节、峰值工作集、句柄/线程/进程数、加载时间、Qt/Python对象及弱引用；加载阶段另100ms采样，关闭后等待对应PID退出再等550ms。证据流式写仓库外JSONL，不把全部循环结果保留内存；跟踪器移除已死亡弱引用。源码指纹在启动时保存，用于确认长期测试的实际产品代码没有变化。

这里的主进程是实际承载Qt的CPython；Windows venv重定向启动器是其父进程，不在该根及后代的进程计数中。私有字节表示PrivateUsage提交量，不等同于私有驻留工作集。采样范围和Windows峰值计数不构成每一次瞬时分配的完整跟踪。

## STEP安全结论

准确声明源码为OCCT7.6.1，提交`d2abb6d844231cb8f29be6894440874a4700e4a5`。WASM与官方发行gitHead中的dist逐字节一致；JS仅换行符不同。当前源码缺少PR1514的方向边循环保护与新增B样条合同验证，不能确认补丁覆盖；CNA记录描述8.0.0rc5且未完整列出旧版本范围，报告人原始通告则将范围写作不高于7.8.1（包含当前7.6.1），两者均单独记录，不能据CNA口径排除当前风险。STL不走OCCT读取器，OBJ/VRML/IGES没有应用入口，STEP相关风险仍在。详见[安全核验](../../third_party/preview/STEP_SECURITY.md)。

旧WASM保持不变，STEP仅开发模式，不开放普通模式。所有既有限额、隔离解析、网络拒绝、当前文件能力路由和源文件只读保护保持。实验内核不接入客户端；没有引入原生CAD DLL。

已实际安装仓库外便携构建工具：CMake3.31.6、Ninja1.11.1.4、Emscripten3.1.69（SDK源码`a36df02dc438e8b02f91122a4c62eeecb6784272`），取固定包装层及PR1514合并源码。`emcmake cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_NINJA_FORCE_RESPONSE_FILE=ON`配置探针、真实编译均执行。旧包装层不能直接处理8.x目录；实验适配266个模块路径、C++17、头文件搜索及移除的TDF_LabelSequence类型后，编译仍因缺少由新OCCT配置生成的Standard_Version.hxx停止。没有得到最终JS/WASM，没有给实验构建作兼容、补丁或可重复构建PASS。下一步须接入完整官方配置及适配测试，不能继续随意补宏/改版本号当成修复。
